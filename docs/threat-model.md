# 個人用公開カレンダーの脅威モデル

## 1. 対象と前提

このリポジトリは、1人が1つのGitHubリポジトリで予定を管理する個人用カレンダーです。GitHub Issuesを予定の正本とし、GitHub Actionsで生成したICSと案内ページをGitHub Pagesから公開します。

想定する規模は次のとおりです。

- 管理者・予定編集者: 1人
- リポジトリ: 1つ
- Openな予定Issue: 通常は数十件、テスト上限は500件
- グループ別カレンダー: 通常は数個、テスト上限は20個
- 同時編集: 原則なし
- 可用性: 個人利用として最後の正常なPagesを維持できればよく、SLAは設けない

この範囲はサービス上の強制上限ではなく、CIで継続的に確認する運用基準です。上限を超えても生成できる場合がありますが、性能と互換性は保証しません。

## 2. 公開モデルの決定

このカレンダーは**公開ICS専用**とします。

- Pagesのindex、`calendar.ics`、グループ別ICSは認証なしで取得できます。
- URLを知る人だけに限定された情報とはみなしません。URLは検索、共有、ブラウザ履歴、アクセスログなどから知られる可能性があります。
- 推測困難なURLをアクセス制御として使用しません。
- 認証付き配信、利用者別権限、token付き購読URL、独自配信サーバーは実装しません。
- 認証付き配信が必要になった場合は、このPages構成へ継ぎ足さず、秘密情報の保存、token失効、rotation、監査、cache制御を含む別設計として再評価します。

## 3. 保護するもの

### 保護対象

- GitHub Actionsで使用する`GITHUB_TOKEN`
- リポジトリのコードとworkflow
- 最後に正常公開されたICS
- IssueからICSへ変換するデータの完全性
- 障害通知・入力エラーコメントの真正性

### 保護対象ではないもの

公開対象のIssueとICSへ入力された予定情報の機密性は保護しません。次の情報は登録しないでください。

- 自宅住所や詳細な現在地
- 通院先、診療内容、健康情報
- 予約番号、チケット番号、本人確認情報
- 非公開の会議URLや参加用password
- アクセストークン、API key、秘密鍵
- 他人の本名、連絡先、行動予定
- 公開によって安全上の問題が生じる予定

## 4. 信頼境界

| 境界 | 信頼するもの | 信頼しない入力 |
| --- | --- | --- |
| GitHub Issue | GitHubによるIssue番号と認証 | タイトル、本文、ラベルの内容 |
| GitHub API | HTTPSとGitHub API | 一時障害、不正JSON、rate limit |
| 生成処理 | リポジトリ内の検証済みコード | Issue由来の日時、URL、TEXT、schema |
| GitHub Actions | GitHubが提供するrunnerとtoken | workflow失敗、同時実行、外部通信障害 |
| GitHub Pages | 正常生成した静的成果物 | 購読者の身元、再取得間隔、URLの秘密性 |
| カレンダーアプリ | RFC 5545の基本的な購読機能 | cache、表示差異、更新タイミング |

## 5. 主な脅威と対策

### 意図しない情報公開

**脅威:** IssueやICSへ秘密情報を入力し、Pagesから誰でも取得できる。

**対策:** Issue Form、README、indexで公開情報であることを明示します。`calendar:private`と`calendar:exclude`はICSへの出力を止めますが、Issue自体の機密性を提供しません。

### ICS・HTMLへの注入

**脅威:** IssueのTEXTやURLによってICS構造またはindexのHTMLを壊す。

**対策:** TEXTの制御文字拒否、改行正規化、RFC 5545 escape、URI検証、HTML escape、75 octet folding、生成後検証を行います。

### 不正日時の静かな公開

**脅威:** 不正形式、逆転した期間、DSTの存在しない・曖昧な時刻を誤った予定として公開する。

**対策:** 公開前にIssue番号付きで拒否し、対象Issueへ修正理由を返します。

### 部分的・破損した公開

**脅威:** 入力エラー、API障害、書き込み失敗により一部だけ更新された成果物を公開する。

**対策:** 全成果物を同じfilesystem上でstaging・検証し、成功後にまとめて置換します。workflowはテストと生成が成功した場合だけPagesへdeployします。

### GitHub APIの一時障害

**脅威:** timeout、rate limit、HTTP 429・5xxにより公開が一時停止する。

**対策:** timeout、限定retry、指数backoff、`Retry-After`、rate limit診断を使用し、失敗時は最後の正常なPagesを維持します。

### token漏えい・過剰権限

**脅威:** tokenをログ・Issueへ表示する、または不要な権限を与える。

**対策:** tokenを引数由来の診断へ含めず、workflow権限をcontents read、issues write、Pages deployに限定します。予定Issueへ秘密情報を入力しません。

### botコメント・通知Issueのなりすまし

**脅威:** 利用者がmarkerを模倣し、botに自分のコメントやIssueを更新させる。

**対策:** 専用markerに加え、作成者が`github-actions[bot]`であることを確認してから更新します。

### 同時実行による古い成果物の公開

**脅威:** 連続したIssue操作で古いworkflowが新しいworkflowより後にdeployされる。

**対策:** workflow全体を`pages` concurrency groupへ入れ、`cancel-in-progress`で古い実行を停止します。個人利用では同時編集を前提にしません。

## 6. 受容するリスク

- GitHub、GitHub Actions、GitHub Pagesのサービス障害
- カレンダーアプリ側の長いcache・再取得間隔
- 公開URLと予定情報が第三者へ共有・収集されること
- SLAを設けないこと
- 500予定・20グループを超えた場合の性能低下
- runnerが強制停止した瞬間など、外部サービス側で完全には制御できない競合

## 7. 再評価条件

次のいずれかが必要になった場合は、この脅威モデルを更新します。

- 非公開または限定公開の予定を配信したい
- 複数人がIssueを編集する
- 複数リポジトリを集約する
- 500予定または20グループを継続的に超える
- 外部サービスや独自サーバーへ移行する
- 参加者、会議URL、健康情報など機密性の高いデータを扱う
