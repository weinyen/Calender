# 現状整理とロードマップ

## 1. 目標

GitHub Issuesを予定の正本（Single Source of Truth）として使い、Issueの作成・編集・Close・ラベル変更を、利用者が購読できるiCalendar（ICS）へ安全かつ継続的に反映することを目指します。

目標を満たした状態では、次の一連の操作が成立します。

1. 利用者がIssue Formから予定を登録する。
2. Issueの編集、Close、Reopen、ラベル変更がカレンダーへ自動反映される。
3. 全体またはグループ別の固定URLを、主要なカレンダーアプリから継続購読できる。
4. 入力不備や公開処理の失敗を管理者がすぐ検知し、安全に復旧できる。
5. 公開範囲、互換性、運用品質がテストと文書で保証される。

## 2. 現在できていること

### 予定の登録と解釈

- 日本語のIssue Formから、開始、終了、タイムゾーン、終日指定、場所、関連URL、説明を入力できます。
- `calendar:event` が付いたOpen IssueをGitHub REST APIから100件単位でページング取得し、Pull Requestを除外します。
- 時刻あり予定は指定タイムゾーンで解釈してUTCへ変換し、終日予定はiCalendarの排他的な終了日へ変換します。
- Issueタイトル先頭の `[予定]` を表示名から除去し、Issue番号とリポジトリ名から安定したUIDを作ります。そのため、Issueを編集しても購読先では同じ予定として識別できます。
- 日時、時間範囲、タイムゾーン、関連URLを検証し、不正なIssueがあれば生成全体を失敗させます。

### 公開対象の制御と分類

- `calendar:exclude` または `calendar:private` が付いたIssueをICSから除外できます。
- `group:<slug>` からグループ別ICSを生成できます。複数グループにも対応しています。
- `group:` と `type:` の値をICSの `CATEGORIES` に出力します。
- 前回存在したグループ用ICSを生成前に削除するため、廃止したグループのファイルが成果物へ残りません。

### ICS生成と自動公開

- 全体用 `calendar.ics` と、グループ別 `calendars/<group>.ics` を生成できます。
- `VEVENT`、UID、更新日時、開始・終了、件名、説明、場所、URL、カテゴリを出力します。
- テキストのエスケープ、CRLF、UTF-8で75 octet以内のcontent line foldingに対応しています。
- Issueの作成・編集・Close・Reopen・ラベル変更、および手動実行を契機にGitHub Actionsが再生成し、GitHub Pagesへデプロイします。
- ローカルではGitHub APIだけでなく、Issue API形式のJSONを入力して再現確認できます。

### 現在のテスト

標準ライブラリの単体テストで、時刻あり予定、終日予定、不正な期間、不正URL、非公開・除外、グループ生成、UTF-8の折り返し、Issue Formの空回答の扱いを確認しています。

## 3. 現時点の制約とリスク

### 優先度: 高

1. **購読互換性を実機で保証していない**
   RFC 5545の基本形式は実装済みですが、Apple Calendar、Google Calendar、Outlookなどでの継続購読試験や、自動検証ツールによる適合性確認はありません。タイムゾーン付き予定はUTCで出力されるため瞬間は保持されますが、元のタイムゾーン名や `VTIMEZONE` は配信されません。
2. **公開情報の安全性は運用依存**
   GitHub Pages上のICSは公開です。`calendar:private` は出力除外であり、公開リポジトリ上のIssue本文を秘匿しません。認証付き・限定公開の購読URLも未対応です。
3. **失敗の通知と可観測性が不足している**
   不正Issueが1件でもあればデプロイを止め、直前のPagesを維持できますが、Actionsログ以外の通知、公開日時、生成件数、最終成功状態を示す仕組みはありません。
4. **GitHub API障害への耐性が限定的**
   APIエラー、rate limit、一時的な通信失敗に対する明示的なtimeout、retry、分かりやすい診断がありません。

### 優先度: 中

5. **Issue Formとparserが日本語見出しへ密結合している**
   見出し名を変更すると既存Issueを解釈できなくなります。フォームschemaのversion管理や移行手段はありません。
6. **日時の境界条件が十分に検証されていない**
   DST移行時の存在しない時刻・重複時刻、非常に長い値、不正な `updated_at`、欠落キーなどの試験がありません。
7. **変更・削除の伝達は再生成結果への依存**
   Closeした予定は次のICSから消えますが、`STATUS:CANCELLED` や `SEQUENCE` による明示的な取消・更新通知はありません。購読アプリごとの差を検証する必要があります。
8. **公開URLの案内ページがない**
   PagesにはICSだけが配置され、利用可能なグループ、最終更新、購読方法、稼働状態を確認できるHTML indexはありません。
9. **CIの品質ゲートはまだ限定的**
   Pull Requestとmainへのpush、および公開前の単体テストは実行しますが、静的解析、型検査、依存関係・Actions更新の自動化はまだありません。

### 優先度: 低

10. **繰り返し予定、リマインダー、参加者には未対応**
    `RRULE`、`VALARM`、`ORGANIZER`、`ATTENDEE` は生成しません。
11. **検索・編集用UIや双方向同期は対象外**
    操作画面はGitHub Issuesのみで、カレンダー側からGitHubへの更新はできません。

## 4. ロードマップ

各フェーズは、前フェーズの完了条件を満たしてから進めます。まず「確実に公開・購読できる」基盤を固め、その後に運用性と機能を拡張します。

### Phase 0: 基準の固定（短期）

**目的:** 現在の挙動を壊さず変更できる状態にする。

- [x] Pull Requestとmainへのpushで単体テストを実行するCIを追加する。
- [x] Issue Formの全項目からICSを生成するfixtureベースのend-to-endテストを追加する。
- [x] 空のカレンダー、複数ページ、複数グループ、古いグループ削除、特殊文字、長い日本語、不正APIデータを試験する。
- RFC 5545 validatorをCIへ組み込むか、validatorが確認する不変条件を自動テスト化する。
- 対応Pythonバージョン、サポート対象カレンダーアプリ、公開仕様を明文化する。

**完了条件:** PRごとに生成ロジックと代表的なICSが自動検証され、失敗した変更をmainへ入れない運用ができる。

### Phase 1: 信頼できる公開MVP（短期）

**目的:** 固定URLを安心して継続購読できる最小製品にする。

- GitHub API呼び出しへtimeout、限定retry、rate limitを含むエラー表示を追加する。
- 生成結果を一時ディレクトリへ作成し、検証成功後に成果物として採用するatomicな生成手順にする。
- `X-WR-CALNAME` を含む全プロパティのescapingとfoldingを網羅的に確認する。
- DSTの曖昧・存在しないローカル時刻を検出し、Issue番号付きで修正方法を表示する。
- Apple Calendar、Google Calendar、Outlookで、追加・編集・Close・Reopen・終日・タイムゾーンを受入試験する。
- [x] workflowへテスト工程を追加し、テスト成功時だけPagesへデプロイする。

**完了条件:** 主要3クライアントで固定URLの購読と変更反映を確認し、一時障害や不正入力で壊れたICSを公開しない。

### Phase 2: 運用性と発見性（中期）

**目的:** 管理者と購読者が状態を自力で把握できるようにする。

- Pagesに、全体・グループ別の購読リンク、最終生成時刻、予定件数、使い方を示すindexページを生成する。
- `webcal://` リンクとHTTPS URLのコピー手段を用意する。
- workflow失敗をGitHub Issue、メール、または利用チームの通知先へ知らせる仕組みを選択可能にする。
- 入力エラーのIssueへ検証結果をCheckまたはコメントで返す。ただしbotの更新によるworkflow loopを防止する。
- 生成件数、除外件数、グループ一覧をjob summaryへ出す。
- フォームschemaにversionを持たせ、見出し変更時の後方互換方針と移行ツールを用意する。

**完了条件:** Actionsログを読まなくても、公開状態、購読URL、入力エラーの修正箇所が分かる。

### Phase 3: 公開制御とスケール（中期）

**目的:** 利用組織と予定数が増えても安全に運用する。

- 「公開ICSのみ」という前提を維持するか、認証付き配信サービスを別途設けるかを脅威モデルとともに決定する。
- 限定公開を実装する場合は、推測困難URLだけに依存せず、token rotation、失効、監査ログ、cache制御を設計する。
- ETagまたは条件付きリクエスト、API retry/backoff、rate limit監視を導入する。
- 大量Issue・大量グループでの性能試験を行い、上限と所要時間を文書化する。
- 同時実行時に古い生成結果が新しい結果を上書きしないことを検証する。

**完了条件:** 想定規模と公開モデルが明文化され、その範囲で性能・障害復旧・アクセス制御を再現可能に検証できる。

### Phase 4: カレンダー機能の拡張（長期・需要ベース）

**目的:** 基盤を複雑にしすぎず、確認された利用者需要へ対応する。

- 更新検出に `SEQUENCE`、取消表現に `STATUS:CANCELLED` を使う方式をクライアント互換性試験の結果に基づき検討する。
- 繰り返し予定（`RRULE`）、リマインダー（`VALARM`）、参加者情報を、それぞれ独立した提案・privacy review・受入試験の後に追加する。
- 多言語フォーム、複数リポジトリ集約、カレンダーごとの表示名や説明を設定可能にする。
- 必要性が確認された場合のみ、GitHub App化または管理UIを検討する。

**完了条件:** 各機能が明確な利用事例を持ち、既存の購読互換性と公開安全性を損なわない。

## 5. 次に着手する推奨Issue

1. **CI: Pull Requestで単体テストを実行する** — Phase 0の品質ゲートを作る。
2. **Test: Issue JSONから公開成果物までのE2E fixtureを追加する** — 実際のフォームとparserの契約を固定する。
3. **Test: ICS適合性と主要クライアントの受入チェックリストを作る** — 「生成できる」から「購読できる」へ進める。
4. **Reliability: GitHub APIにtimeout・retry・診断を追加する** — 一時障害と恒久エラーを区別する。
5. **Validation: DST境界の不正・曖昧時刻を拒否する** — 誤った時刻の静かな公開を防ぐ。
6. **Pages: 購読リンクと最終更新を示すindexを生成する** — URLの発見性と運用確認を改善する。

## 6. スコープ判断の原則

- **公開前提を明示する:** 認証なしGitHub Pagesを使う限り、ICSとそこに含む情報は公開情報として扱います。
- **互換性を推測しない:** RFC上妥当でもクライアント挙動は異なるため、主要クライアントの受入試験を完了条件に含めます。
- **Issueを正本に保つ:** 生成物を手編集せず、同じIssue番号のUIDを安定させます。
- **失敗時は最後の正常版を守る:** 一部だけ生成した成果物や検証前の成果物を公開しません。
- **高度な機能より運用品質を優先する:** 繰り返し予定などの追加前に、CI、検証、通知、可観測性を完成させます。
